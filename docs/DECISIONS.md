# Sense Vocab 决策记录

本文件只记录已经确定、会影响后续工作的长期决策。新决策追加，不重写历史；被替代时标记“已取代”并指向新决策。

## D-001 四部门对话模型

- 日期：2026-08-08
- 状态：生效
- 决策：项目分为 PMO、R&D、OP、CD 四个独立对话。用户通过打开对话主动选择部门；一个部门工作时不自动唤起其他部门。
- 原因：降低长对话噪声，让需求、研发、维护和内容各自保留高价值上下文。
- 影响：不建立严格文件所有权，也不强制所有产物交由 OP 审核。每个部门可完成任务所需的相邻工作。

## D-002 仓库文档是跨对话共享记忆

- 日期：2026-08-08
- 状态：生效
- 决策：新对话使用干净上下文，通过 `AGENTS.md`、`PROJECT_CONTEXT.md`、`CURRENT.md`、`DECISIONS.md` 和部门章程继承项目知识。Archived 对话保留为历史证据，不作为日常事实源。
- 原因：对话分支会继承大量低价值历史并迅速再次膨胀；仓库文档可审查、可版本化、可被所有对话读取。
- 影响：重大实现或决策完成后，要同步维护相应文档。

## D-003 正式工作区单写入者

- 日期：2026-08-08
- 状态：生效
- 决策：同一时刻只允许一个对话写 `D:\Files\sense-vocab-mvp`。并行编码使用独立 worktree；并行只读分析不受限制。
- 原因：各部门不设硬文件边界时，单写入者是避免覆盖、半成品部署和状态滞后的最小约束。

## D-004 部署即时、版本按日聚合

- 日期：2026-08-06
- 状态：生效
- 决策：每次验证完成的修改可以立即部署公网；GitHub 版本、tag 和 Release 每个香港自然日最多一次，由 OP 晚间自动化汇总。
- 原因：用户需要快速修复线上问题，同时避免一天内频繁产生版本和版本号断层。
- 影响：R&D、OP、CD 的日间工作不得随手提高版本号；README、CHANGELOG、package 与 lockfile在正式发布时统一更新。

## D-005 发布前反馈门禁

- 日期：2026-08-05
- 状态：生效
- 决策：每日发布前先只读检查后台新建/未处理反馈，复现并修复真实问题。认证、权限、网络、必要数据或验证受阻时停止发布。
- 原因：不能在已知用户问题未处理时自动宣称版本完成。
- 影响：不得调用带清理副作用的反馈列表方法做门禁，不得删除反馈或学习数据；只在修复验证后条件更新对应状态。

## D-006 义项级 double check

- 日期：2026-08-05
- 状态：生效
- 决策：采用 `new -> reinforce -> review -> mastered` 的义项状态机，并区分“强化后次日复习确认”和“强化未确认、仅次日复习确认”两条路径。
- 原因：一次认识不足以证明稳定掌握，同时不能让已经完成两次确认的义项继续重复。
- 影响：详细转换以 `PROJECT_CONTEXT.md` 为准，任何学习流程改动必须增加跨多个学习日的回归测试。

## D-007 学习日与自然日分离

- 日期：2026-07-26
- 状态：生效
- 决策：自然日期不人工推进；复习到期使用学习日；跨午夜学习归入开始日期。新词计划按实际引入数量滑动，不丢弃未完成窗口。
- 原因：解决提前学习、缺席、不完整学习和跨午夜时进度口径不一致。

## D-008 共用义项池、词书独立状态

- 日期：2026-07-28
- 状态：生效
- 决策：多词书共用单词和义项身份，每本词书仅维护引用；计划、义项状态、活动和统计按词书隔离。
- 原因：减少重复内容维护，同时保证同一用户在不同考试目标下独立学习。
- 影响：既有考研 ID 和数据范围是兼容性边界；新增词书不能改写考研原始数据。

## D-009 本地优先写入与保守云合并

- 日期：2026-07-31
- 状态：生效
- 决策：游客使用 localStorage；账户使用独立本地缓存和云端快照。云保存使用 CAS 和设备版本向量，冲突时合并；同一义项分歧采用更保守状态。
- 原因：支持离线、多设备和恢复，同时避免空白或旧设备覆盖完整记录。
- 影响：任何压缩、迁移和恢复必须先保留真实来源，不得在写入成功前删除旧值。

## D-010 教程数据隔离

- 日期：2026-07-29
- 状态：生效
- 决策：教程使用独立临时数据，结束或退出后不改变真实计划、进度、活动和云端记录。
- 原因：教程需要可重复，但不能污染新用户或老用户的数据。

## D-011 高辨识度例句

- 日期：2026-07-09
- 状态：生效
- 决策：每个义项同时提供释义和真正的语境例句。例句必须通过相关动作、对象和场景提示该义项，并与同词其他义项尽量不兼容；难度按目标人群控制。
- 原因：模板句和纯释义信息熵低，不能帮助区分和长期记忆。

## D-012 合规替换不得静默减配

- 日期：2026-07-29
- 状态：生效
- 决策：发现来源或授权风险时，优先以合法可商用数据或原创内容替换，并保持功能和数据兼容。没有等价替代时记录风险，不通过直接停用造成释义、例句、翻译或发音缺失。
- 原因：合规治理与产品可用性必须同时满足，不能用删除功能掩盖来源问题。

## D-013 README 与版本更新记录分离

- 日期：2026-08-08
- 状态：生效
- 决策：`README.md` 始终作为长期有效的项目简介，只维护产品定位、稳定核心能力、使用方法、架构、部署、安全和兼容性等长期事实；GitHub Release 是正式版本的新功能、问题修复、内容调整、维护记录、兼容性说明和验证结果的唯一权威来源。`CHANGELOG.md` 保留 `v1.3.1` 及以前的历史记录，后续不再逐版追加。
- 原因：把逐版本公告持续写入 README 会稀释项目介绍、造成重复维护和文档漂移；Release 更适合承载与 tag 对应的完整更新记录。
- 影响：D-004 的即时部署、香港自然日每日唯一版本和 OP 聚合职责继续生效；其中“每次发布同步 README 与 CHANGELOG”的要求由本决策取代。正式发布仍同步 `package.json` 与 `package-lock.json`，但只有长期项目事实改变时才更新 README，README 与历史 CHANGELOG 均不再要求和每个版本号机械对齐。

## D-014 发布前采用任务状态租约与有界等待

- 日期：2026-08-08
- 状态：生效
- 决策：正式工作区的临时写入租约以 Codex App 中同一 `cwd` 的任务当前轮次状态为事实源。任务 ID、轮次开始时间、最近更新时间和 active/idle/needs-attention 状态分别承担持有者、取得时间、心跳和租约状态；任何写入、可能写文件的命令、数据库迁移或部署尚未结束时均视为 `HELD`，本轮所有工具和进程结束后由任务在最终回复明确标记 `RELEASED`。23:30 OP 自动化发现自身和 Archived 之外的同工作区任务仍 active 时，使用任务等待工具进行事件式等待，总上限 30 分钟；等待期间不得向其他部门发送消息、唤起任务、修改工作区或高频轮询。每次有任务完成后重新检查全部同工作区任务，直到全部释放或达到截止时间。
- 原因：仅凭一次 `git status` 无法判断另一任务是否仍在测试、迁移或部署；立即停止会漏掉即将完成的日间改动，高频轮询又增加 Token 和上下文成本。任务状态提供现成的持有者与心跳信息，事件等待可以在不自动调度其他部门的前提下避免并发写入。
- 影响：不新增需要提交或清理的运行时锁文件。任务需要用户处理、状态不可读、租约含义不明确或 30 分钟超时时，自动化必须停止发布并将改动顺延到下次日更。`RELEASED` 只证明当前轮次不会继续写入；自动化仍须根据最终 diff、测试和共享文档判断改动是否完整、是否可发布，并在取得 OP 发布租约后重新执行全部门禁。

## D-015 义项身份不依赖展示顺序

- 日期：2026-08-09
- 状态：生效
- 决策：运行时义项 ID 通过既有 ID、synset、词性和语义内容匹配保持稳定，不得根据当前数组位置或用户看到的“第几条”重新编号。内容构建复用所有可匹配的历史 ID，只为真正新增的义项分配新 ID。
- 原因：用户学习会改变义项展示顺序，内容维护也可能插入新义项；位置不是稳定身份，把位置当身份会把反馈修到错误义项，或使既有学习记录错绑。
- 影响：旧版位置式反馈必须结合词性、释义、例句和 synset 做语义判断；结构化反馈继续携带稳定 `senseId`。词库发布前必须验证既有单词和义项 ID 全部保留，并把顺序变化与身份变化分开审计。
