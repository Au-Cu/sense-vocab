# Sense Vocab 决策记录

本文件只记录已经确定、会影响后续工作的长期决策。新决策追加，不重写历史；被替代时标记“已取代”并指向新决策。

## D-001 四部门对话模型

- 日期：2026-08-08
- 状态：已由 D-016 取代
- 决策：项目分为 PMO、R&D、OP、CD 四个独立对话。用户通过打开对话主动选择部门；一个部门工作时不自动唤起其他部门。
- 原因：降低长对话噪声，让需求、研发、维护和内容各自保留高价值上下文。
- 影响：不建立严格文件所有权，也不强制所有产物交由 OP 审核。每个部门可完成任务所需的相邻工作。

## D-002 仓库文档是跨对话共享记忆

- 日期：2026-08-08
- 状态：生效
- 决策：新对话使用干净上下文，通过 `AGENTS.md`、`PROJECT_CONTEXT.md`、`CURRENT.md`、`DECISIONS.md` 和部门章程继承项目知识。Archived 对话保留为历史证据，不作为日常事实源。
- 原因：对话分支会继承大量低价值历史并迅速再次膨胀；仓库文档可审查、可版本化、可被所有对话读取。
- 影响：重大实现或决策完成后，要同步维护相应文档。

## D-003 正式工作区单写入者

- 日期：2026-08-08
- 状态：生效
- 决策：同一时刻只允许一个对话写 `D:\Files\sense-vocab-mvp`。并行编码使用独立 worktree；并行只读分析不受限制。
- 原因：各部门不设硬文件边界时，单写入者是避免覆盖、半成品部署和状态滞后的最小约束。

## D-004 部署即时、版本按日聚合

- 日期：2026-08-06
- 状态：生效
- 决策：每次验证完成的修改可以立即部署公网；GitHub 版本、tag 和 Release 每个香港自然日最多一次，由 OP 晚间自动化汇总。
- 原因：用户需要快速修复线上问题，同时避免一天内频繁产生版本和版本号断层。
- 影响：R&D、OP、CD 的日间工作不得随手提高版本号；README、CHANGELOG、package 与 lockfile在正式发布时统一更新。

## D-005 发布前反馈门禁

- 日期：2026-08-05
- 状态：生效
- 决策：每日发布前先只读检查后台新建/未处理反馈，复现并修复真实问题。认证、权限、网络、必要数据或验证受阻时停止发布。
- 原因：不能在已知用户问题未处理时自动宣称版本完成。
- 影响：不得调用带清理副作用的反馈列表方法做门禁，不得删除反馈或学习数据；只在修复验证后条件更新对应状态。

## D-006 义项级 double check

- 日期：2026-08-05
- 状态：生效
- 决策：采用 `new -> reinforce -> review -> mastered` 的义项状态机，并区分“强化后次日复习确认”和“强化未确认、仅次日复习确认”两条路径。
- 原因：一次认识不足以证明稳定掌握，同时不能让已经完成两次确认的义项继续重复。
- 影响：详细转换以 `PROJECT_CONTEXT.md` 为准，任何学习流程改动必须增加跨多个学习日的回归测试。

## D-007 学习日与自然日分离

- 日期：2026-07-26
- 状态：生效
- 决策：自然日期不人工推进；复习到期使用学习日；跨午夜学习归入开始日期。新词计划按实际引入数量滑动，不丢弃未完成窗口。
- 原因：解决提前学习、缺席、不完整学习和跨午夜时进度口径不一致。

## D-008 共用义项池、词书独立状态

- 日期：2026-07-28
- 状态：生效
- 决策：多词书共用单词和义项身份，每本词书仅维护引用；计划、义项状态、活动和统计按词书隔离。
- 原因：减少重复内容维护，同时保证同一用户在不同考试目标下独立学习。
- 影响：既有考研 ID 和数据范围是兼容性边界；新增词书不能改写考研原始数据。

## D-009 本地优先写入与保守云合并

- 日期：2026-07-31
- 状态：生效
- 决策：游客使用 localStorage；账户使用独立本地缓存和云端快照。云保存使用 CAS 和设备版本向量，冲突时合并；同一义项分歧采用更保守状态。
- 原因：支持离线、多设备和恢复，同时避免空白或旧设备覆盖完整记录。
- 影响：任何压缩、迁移和恢复必须先保留真实来源，不得在写入成功前删除旧值。

## D-010 教程数据隔离

- 日期：2026-07-29

- 原因：教程需要可重复，但不能污染新用户或老用户的数据。

## D-011 高辨识度例句

- 日期：2026-07-09
- 状态：生效
- 决策：每个义项同时提供释义和真正的语境例句。例句必须通过相关动作、对象和场景提示该义项，并与同词其他义项尽量不兼容；难度按目标人群控制。
- 原因：模板句和纯释义信息熵低，不能帮助区分和长期记忆。

## D-012 合规替换不得静默减配

- 日期：2026-07-29
- 状态：生效
- 决策：发现来源或授权风险时，优先以合法可商用数据或原创内容替换，并保持功能和数据兼容。没有等价替代时记录风险，不通过直接停用造成释义、例句、翻译或发音缺失。
- 原因：合规治理与产品可用性必须同时满足，不能用删除功能掩盖来源问题。

## D-013 README 与版本更新记录分离

- 日期：2026-08-08
- 状态：生效
- 决策：`README.md` 始终作为长期有效的项目简介，只维护产品定位、稳定核心能力、使用方法、架构、部署、安全和兼容性等长期事实；GitHub Release 是正式版本的新功能、问题修复、内容调整、维护记录、兼容性说明和验证结果的唯一权威来源。`CHANGELOG.md` 保留 `v1.3.1` 及以前的历史记录，后续不再逐版追加。
- 原因：把逐版本公告持续写入 README 会稀释项目介绍、造成重复维护和文档漂移；Release 更适合承载与 tag 对应的完整更新记录。
- 影响：D-004 的即时部署、香港自然日每日唯一版本和 OP 聚合职责继续生效；其中“每次发布同步 README 与 CHANGELOG”的要求由本决策取代。正式发布仍同步 `package.json` 与 `package-lock.json`，但只有长期项目事实改变时才更新 README，README 与历史 CHANGELOG 均不再要求和每个版本号机械对齐。

## D-014 发布前采用任务状态租约与有界等待

- 日期：2026-08-08
- 状态：生效
- 决策：正式工作区的临时写入租约以 Codex App 中同一 `cwd` 的任务当前轮次状态为事实源。任务 ID、轮次开始时间、最近更新时间和 active/idle/needs-attention 状态分别承担持有者、取得时间、心跳和租约状态；任何写入、可能写文件的命令、数据库迁移或部署尚未结束时均视为 `HELD`，本轮所有工具和进程结束后由任务在最终回复明确标记 `RELEASED`。23:30 OP 自动化发现自身和 Archived 之外的同工作区任务仍 active 时，使用任务等待工具进行事件式等待，总上限 30 分钟；等待期间不得向其他部门发送消息、唤起任务、修改工作区或高频轮询。每次有任务完成后重新检查全部同工作区任务，直到全部释放或达到截止时间。
- 原因：仅凭一次 `git status` 无法判断另一任务是否仍在测试、迁移或部署；立即停止会漏掉即将完成的日间改动，高频轮询又增加 Token 和上下文成本。任务状态提供现成的持有者与心跳信息，事件等待可以在不自动调度其他部门的前提下避免并发写入。
- 影响：不新增需要提交或清理的运行时锁文件。任务需要用户处理、状态不可读、租约含义不明确或 30 分钟超时时，自动化必须停止发布并将改动顺延到下次日更。`RELEASED` 只证明当前轮次不会继续写入；自动化仍须根据最终 diff、测试和共享文档判断改动是否完整、是否可发布，并在取得 OP 发布租约后重新执行全部门禁。

## D-015 义项身份不依赖展示顺序

- 日期：2026-08-09
- 状态：生效
- 决策：运行时义项 ID 通过既有 ID、synset、词性和语义内容匹配保持稳定，不得根据当前数组位置或用户看到的“第几条”重新编号。内容构建复用所有可匹配的历史 ID，只为真正新增的义项分配新 ID。
- 原因：用户学习会改变义项展示顺序，内容维护也可能插入新义项；位置不是稳定身份，把位置当身份会把反馈修到错误义项，或使既有学习记录错绑。
- 影响：旧版位置式反馈必须结合词性、释义、例句和 synset 做语义判断；结构化反馈继续携带稳定 `senseId`。词库发布前必须验证既有单词和义项 ID 全部保留，并把顺序变化与身份变化分开审计。

## D-016 五部门对话模型

- 日期：2026-08-09
- 状态：生效
- 决策：在 PMO、R&D、OP、CD 之外新增 `LC｜法务合规` 独立对话，按计划商业发行的标准审查适用法律法规、第三方内容与软件权利链、隐私和数据处理、AI 生成内容及其他商业发布风险。用户仍通过打开对话主动选择部门；任何部门工作时都不自动创建、唤起、通知或要求其他部门同时响应。
- 原因：商业发行合规需要持续核对会变化的法律、监管要求、许可证和供应商条款，并把事实、法律解释、证据缺口和发布阻断项与内容生产、产品研发和运行维护分开管理。
- 影响：D-001 的四部门数量由本决策取代，其不自动调度、不建立严格文件所有权、允许当前部门完成必要相邻工作的原则继续生效。LC 默认以只读审查和证据记录为主，不代表外部律师，不自动联系权利人、监管机构或供应商，也不自行签约、购买许可、提交备案或发布版本。

## D-017 可审计合规台账与知识内容双层门禁

- 日期：2026-08-09
- 状态：生效
- 决策：法律/合规风险矩阵与第三方权利链使用可版本化、可审计的共享台账记录项目判断和证据索引；法律法规、许可证、合同、授权书及其他可核验一手材料仍是判断依据，任何后台页面都只作为台账的展示与流程入口，不形成独立法律事实源。风险分级结论与整改进度分开记录；`CLEARED` 必须绑定适用内容、版本、渠道、商业模式、日期、审查人和证据，风险接受不能豁免法律、合同、必要授权、用户同意或主管部门许可。任何知识内容字段的新增或修改都必须同时通过内容正确性、稳定 `wordId`/`senseId` 兼容和字段级权利链门禁；用户反馈只是问题线索，不构成第三方内容使用授权。
- 原因：当前历史内容仍存在全局商业权利阻断，如果把普通维护与收费商业发行使用同一全局门禁，会冻结无关修复；如果只检查内容正确性，又可能在修复 Bug 时引入新的侵权内容或破坏既有用户数据。共享台账和字段级证据可以让结论可追溯，同时把法律依据、项目判断与后台操作分开。
- 影响：普通日间内容维护采用变更集门禁：实际新增或修改的字段必须具备必要权利证据且不得保留未解决的 `BLOCKER/HIGH`，本次变更不得新增或加重风险；未触及的历史阻断继续留在台账，但不冻结无关维护。收费商业发行采用拟发行范围的全局门禁，所有未解决 `BLOCKER/HIGH` 必须清零。结论、证据状态和整改记录通过追加新记录或明确取代旧记录保留历史，不得静默覆盖；缺少必要证据不得标记 `CLEARED`。因个人信息、安全事件、法定保存期限或其他适用义务确需删除材料时，必须经过授权，并在法律允许范围内保留删除原因、范围和审计事件。具体存储格式、数据库结构、工作流枚举、管理员权限和后台交互由后续实现确定；在部署和可重复验证前不得写成现有产品能力。除 D-018 明确规定的单次 CD 候选生成请求外，本决策不改变 D-016 的不自动调度与无严格文件所有权原则。

## D-018 知识内容反馈的单次 CD 候选生成与人工审核

- 日期：2026-08-12
- 状态：生效
- 决策：当反馈涉及缺失或错误义项、释义、例句、翻译、音标、词形或发音，且 OP 已用稳定 `wordId`、`senseId`、synset、词性和语义确认真实对象并确定需要生成合法替换内容时，OP 可以向既有 CD 对话发送一次匿名化、候选生成专用请求。这是 D-016 不自动调度原则的唯一内容修复例外；不得创建新的部门任务，不得扩展到 LC、R&D 或 PMO。同一次反馈检查或维护批次存在多项待生成内容时，OP 必须先完成定位、按稳定内容 ID 去重并汇总为一个批量请求，不得按反馈记录、单词、义项或字段逐条递交；当前批次确实只有一项时才发送单项请求。CD 只返回按批次项编号和稳定内容 ID 对齐的逐字段候选及生成证据，不修改正式工作区、生产反馈、用户数据、部署或版本。OP 收到候选后停止当前修复或自动发布流程，等待用户对明确候选作出人工审核；只有用户明确通过后，OP 才能按批准内容实施修改。
- 原因：由 CD 负责语言内容生成可以避免 OP 临时拼写内容，但模型或部门输出本身既不等于内容正确，也不等于获得输入权、输出权或商业再分发授权。把用户审核设为实施前的硬门禁，可以同时保留内容职责边界、人工判断和可追溯证据。
- 影响：批量请求只携带排查所需的匿名化结构信息，并为每一项列出批次项编号、稳定内容 ID、目标字段、允许使用的输入材料或证据位置及验收标准，不得转发反馈原文、用户身份、附件地址、令牌或其他隐私。CD 交付必须按同一批次结构列明候选字段、模型/版本、供应商或权重来源、输入材料及其许可证或权属依据、生成批次、可复现提示词或提示词哈希、候选输出哈希和剩余风险，不能把多项内容合并成无法逐字段审核的一段文本。用户可以逐项或逐字段批准；OP 只实施明确批准部分，未批准、被驳回或证据不足的项目继续保持未解决。批准后，OP 逐字段记录用途、作者或权利人、直接来源、获取日期、许可证名称与版本及商业使用/修改/缓存/传播/再分发范围、署名或 ShareAlike/NOTICE 义务、修改说明、新旧值哈希、证据位置、经办与复核信息；随后运行内容身份、权利台账、内容审计、专项检查、构建、测试和用户可见验证。任何候选、批准、证据或验证缺失时，对应反馈保持未解决或证据待补，本次自动化停止且不发布。

## D-019 生成内容安全与目标义项强绑定

- 日期：2026-08-12
- 状态：生效
- 决策：所有新增或改写的中文义项、英文释义、释义译文、例句和例句译文，无论来自人工原创、AI、机器翻译、模板还是第三方材料改编，都必须先绑定稳定内容 ID、词性和目标义项，并逐字段及跨字段确认没有漂移到同词其他义项。生成内容不得涉及性行为、性暗示、色情或性化描写；仅当目标义项本身不可避免属于性相关语义时，允许使用解释该义项所必需的中性、非露骨、适龄表达。生成内容不得包含中国政治或意识形态相关人物、组织、制度、政策、事件、口号、立场或叙事。
- 原因：内容即使语法正确或单字段看似合理，也可能因模板、翻译或多义词消歧失败而错绑义项；无关的敏感场景既降低教学适配性，也会给产品带来不必要风险。
- 影响：D-018 候选生成、普通 CD 内容任务和内容生成脚本都受本决策约束。例句中的目标词必须实际使用目标词性和目标含义，中文字段必须忠实对应各自英文原文且保持同一义项。任何歧义、义项漂移、无关性内容或中国政治/意识形态内容均为候选阻断项；不能安全生成时停止该项并转人工处理，不得用隐晦影射、删除必要字段或合并义项绕过，人工审核也不构成禁用内容例外。D-018 每个候选项还必须记录目标义项绑定、相邻义项排除、性相关判定及中国政治/意识形态判定，供用户逐项审核。自动关键词或相似度检查只能作初筛，不能替代逐项语义复核。本决策自生效日起约束新增和改写字段，不据此自动宣称未触及的历史内容已经复核通过。

## D-020 风险分级验证与同源结果复用

- 日期：2026-08-12
- 状态：生效
- 决策：所有部门按任务实际影响采用同一验证分级，并以命中的最高等级为准：`T0` 为只改文档、Prompt 或注释；`T1` 为只修改既有义项的内容字段，不新增、删除或合并义项，也不改变稳定 ID、synset、词书引用、音频、代码或数据结构；`T2` 为义项新增、删除、合并，或改变 synset、词书引用、音频及其他内容结构；`T3` 为产品代码、学习状态机、账户同步、数据库、鉴权、安全、构建链或依赖变化；`T4` 为 GitHub 正式版本或收费商业发行。迭代阶段运行与受影响范围匹配的针对性验证；面向公网的最终产品或内容状态仍按现行规则完成构建、完整测试和适用专项门禁。每项门禁只依赖与其结果有关的输入；成功结果只有在相关源码、内容、依赖锁、测试配置、工具版本和构建产物等输入均未变化，且命令、结果、时间和输入证据可复核时才可复用。任一相关输入变化、证据缺失、结果不可复现或适用范围扩大后，该项结果立即失效。
- 原因：流程审核确认，稳定 ID、字段级权利链、内容人工复核、用户数据保护和正式发布核验均有真实必要性；耗时冗余主要来自部门章程与 Prompt 重复描述、同一检查在显式命令、构建和部署间重复执行、与改动无关的全局产物反复生成，以及小范围维护与大型集成发布未分级。按风险选择检查并复用同一输入的可核验证据，可以缩短日常维护时间，而不降低最终产物的保证强度。
- 影响：`T0` 不运行无关产品构建或浏览器测试；`T1` 聚焦实际变更字段的语义、D-019、稳定身份、字段级权利链和针对性回归；`T2` 在 `T1` 基础上增加历史用户兼容、词书范围、学习路径及相关桌面/手机验证；`T3` 增加受影响代码、数据库、同步、安全或构建专项验证；`T4` 对最终拟发布状态完成正式版本、tag、Release 和远端一致性核验，收费商业发行还必须通过 D-017 的拟发行范围全局门禁。只有改动影响用户可见界面或交互时才要求对应视口验证，只有触及数据库、安全、依赖或第三方来源时才追加相应专项门禁。批次公共的模型、供应商、许可证和证据可以集中记录并由字段引用，但每个字段仍须保留稳定内容 ID、字段名、新旧值哈希和审核结论。普通维护结果不得扩张为收费商业发行清关，验证复用不得削弱 D-003、D-005、D-012、D-014、D-015、D-017、D-018 或 D-019。
- 实现边界：本决策规定工作原则，不代表参数化变更集校验器、自动验证凭据、按哈希缓存、纯只读 `verify` 命令或“部署已验证产物”入口已经实现。相关能力在代码、自动化和可重复验证落地前必须标记为待实现；现有脚本仍按其真实行为执行，不得主观跳过内部门禁。后续工具应把会写产物的 `build` 与只读 `verify` 分离，并让每项验证明确记录自己的相关输入，而不是依赖“同一天已经运行”等模糊判断。

## D-021 永久规则变更的主动文档落点评估

- 日期：2026-08-12
- 状态：生效
- 决策：用户已经明确确认或当前实现已经可重复验证的永久工作流程、跨任务抽象准则、部门职责或协作方式发生变化时，负责当前任务的部门必须在同一任务中主动评估并同步必要的共享文档，不等待用户再次提出“写入 MD”。跨部门长期规则或需要保留原因与取代关系的决策追加到 `DECISIONS.md`；长期产品与架构不变量写入 `PROJECT_CONTEXT.md`；部门特有职责或工作方式只写入对应 `docs/departments/*.md`；当前版本、部署、自动化、风险、阻断与实施进度写入 `CURRENT.md`；只有影响所有任务启动与协作的入口规则才同步 `AGENTS.md`。同一规则需要多个落点时，以 `DECISIONS.md` 或 `PROJECT_CONTEXT.md` 中的规范定义为准，其他文件只保留本层必要差异和引用，不机械复制全文。
- 原因：永久规则只留在聊天中会在新任务、自动化或部门切换后丢失；把同一长规则复制到所有文件又会造成漂移、冲突和额外上下文成本。主动判断最小规范落点，可以让后续任务自动继承，同时保持事实源清晰。
- 影响：已经生效的长期规则同步文档属于该规则变更的正常收尾，不需要用户逐文件再次授权；但本决策不授权代码实现、数据库修改、部署、发布、外部联络或其他超出原任务的动作。用户明确要求本轮只读时，只报告推荐落点并等待落地授权。尚未确认的建议、一次性排查方法、临时例外和未实现能力不得写成现有规则或能力；需要记录当前计划或阻断时只能在 `CURRENT.md` 明确标为待实现。历史决策不直接改写，通过追加新决策说明取代或补充关系。
