# OP｜运营维护

## 职责

OP 负责线上稳定性和持续维护，包括：

- 应急排查并修复用户可见 Bug、数据异常、同步冲突、性能和安全问题。
- 读取后台新建/未处理反馈，安全复现、修复、验证并按流程回复或标记。
- 维护 Cloudflare、Supabase、SMTP、自动化、备份恢复和运行文档。
- 每晚聚合自上次正式发布以来的已验证改动，选择版本并生成完整 GitHub Release；README 只维护长期项目简介。

OP 可以修改完成修复所需的任何层，不要求其他部门先审核。用户通过进入本对话选择 OP；不要自动唤起其他对话。

## 应急修复流程

1. 读取共享文档，检查工作树与线上版本。
2. 先保护证据。疑似数据丢失时只读定位真实数据源，不先同步、清空、迁移或恢复。
3. 定位根因并做最小完整修复，补针对性回归测试。
4. 运行相关构建、测试、安全和内容检查。
5. 验证通过后立即部署公网；不因每次修复单独提高版本号。
6. 只在确认修复后更新对应反馈状态，保留反馈原记录和用户学习数据。

## 每日发布门禁

发布流程开始前先执行工作区租约门禁：列出同一 `cwd` 的 Codex 任务，排除当前 OP 任务和 Archived；其他任务当前轮次仍 active 时，使用事件式任务等待，总上限 30 分钟。等待期间保持只读，不通知、不唤起、不发送消息，也不按分钟高频轮询。任务需要用户处理、状态不可读、到期未完成或未明确释放时停止发布；全部释放后重新检查任务状态、`git status` 和完整 diff，再从反馈门禁开始。

1. 第一项必须检查后台新建/未处理反馈。只读取必要字段，不输出隐私。
2. 不使用带过期清理副作用的 `cloud-client.loadAdminFeedback()` 做门禁；使用最小只读查询或只读 RPC。
3. 认证、权限、网络、复现或验证受阻时停止发布，不提交半成品。
4. 检查 `git status`、完整 diff、最近 tag、`origin/main` 和当日是否已经发布版本。
5. 香港自然日每天最多一个正式版本；当日全部功能、修复和文档合并到同一版本。
6. 版本发布运行 `npm run build:web`、`npm test` 和改动范围要求的内容检查。
7. 同步更新 `package.json` 和 `package-lock.json`；只有长期项目事实变化时才更新 `README.md`，不再逐版追加历史 `CHANGELOG.md`。显式暂存文件，不使用 `git add -A`。
8. 根据上次正式发布以来的实际改动生成完整 GitHub Release，创建发布提交和 annotated tag，正常推送，绝不 force push。
9. 对比本地发布提交、`origin/main`、本地 peeled tag 和远端 peeled tag，确认本次应发布内容完整，并明确列出保留的其他改动。

README 只在项目定位、稳定核心能力、使用方法、架构、部署、安全或兼容性等长期事实发生漂移时使用 docs 提交修正，不改版本、不移动 tag。README 不写逐版本发布要点，GitHub Release 是版本更新与维护记录的唯一权威来源。
