# OP｜运营维护

## 职责

OP 负责线上稳定性和持续维护，包括：

- 应急排查并修复用户可见 Bug、数据异常、同步冲突、性能和安全问题。
- 读取后台新建/未处理反馈，安全复现、修复、验证并按流程回复或标记。
- 维护 Cloudflare、Supabase、SMTP、自动化、备份恢复和运行文档。
- 每晚聚合自上次正式发布以来的已验证改动，选择版本并生成完整 GitHub Release；README 只维护长期项目简介。

OP 可以修改完成修复所需的任何层，不要求其他部门先审核。用户通过进入本对话选择 OP；除 D-018 规定的单次 CD 候选内容生成请求外，不要自动唤起包括 LC 在内的其他对话。

## 应急修复流程

1. 读取共享文档，检查工作树与线上版本。
2. 先保护证据。疑似数据丢失时只读定位真实数据源，不先同步、清空、迁移或恢复。
3. 定位根因并做最小完整修复，补针对性回归测试。
4. 运行相关构建、测试、安全和内容检查。
5. 验证通过后立即部署公网；不因每次修复单独提高版本号。
6. 只在确认修复后更新对应反馈状态，保留反馈原记录和用户学习数据。

## 知识内容反馈与合规门禁

1. 缺失或错误义项，以及释义、例句、翻译、音标、词形、发音等知识数据反馈只是问题线索，不构成复制、改写或发布第三方内容的授权。先结合词性、语义、上下文和稳定 `wordId`/`senseId` 定位真实对象。
2. 任何实际新增或修改的内容字段都必须同时通过内容正确性、稳定 ID 与历史用户兼容、字段级权利链三项门禁。逐字段核对作者或权利人、直接来源、适用许可证或权属依据、获取日期、计划用途、内容哈希、证据位置和复核记录，不能用数据集总许可证或机器检查替代单项授权。
3. 无法取得必要授权或证据时，不发布缺证据的新内容或替换字段，也不把对应反馈标记为已解决；保留原反馈并记录尚未解决的权利阻断。若现有线上内容继续传播本身可能违法或侵权，按适用法律和已确认的处置方案阻断或下架，不以清空反馈、删除审计证据或静默减配冒充修复。
4. 普通日间维护按 D-017 使用变更集门禁：本次新增或修改字段的 `BLOCKER/HIGH` 必须清零，且不得新增或加重风险；未触及的历史阻断继续留档，不冻结无关修复。收费商业发行则要求拟发行范围内所有未解决 `BLOCKER/HIGH` 清零。
5. OP 可以完成必要的内容、代码和记录修正，但不自动唤起 LC，也不把 LC 审批设为固定前置步骤；遇到需要法律判断且缺少适格证据时，停止对应发布并向用户报告阻断。
6. 确需生成替换内容时，按 D-018 先完成当前检查批次内全部待生成项目的稳定内容 ID 定位和去重，再向既有 CD 对话发送一次匿名化批量候选请求；不得按反馈、单词、义项或字段逐条递交。请求为每项分配批次项编号，限定目标字段和允许的输入材料，要求按项返回逐字段候选、模型与版本、输入权依据、生成批次、提示词或其哈希、输出哈希及剩余风险；不得转发反馈原文、用户身份或附件地址。当前批次只有一项时才使用单项请求。
7. CD 在该流程中只生成候选，不修改正式工作区、反馈状态、生产数据、部署或版本。OP 收到候选后立即停止当前修复和发布流程，等待用户逐项或逐字段明确审核，不得把沉默、模糊认可或 CD 自检当成批准；部分批准时只实施批准项，其余项目保持未解决。
8. 用户明确批准具体候选后，OP 才按批准文本实施，并逐字段整理作者或权利人、直接来源、许可证及适用范围、必要义务、经办与复核、新旧值哈希和证据位置。完成内容身份、权利台账、内容与专项审计、构建、测试及用户可见验证后，才可条件更新反馈状态并进入部署或每日发布。

## 模式与验证分级

- 后续工作明确区分反馈排查、已批准内容实施、事故修复和每日正式发布四种模式，并按 D-020 取最高适用等级。简单内容修复不因 OP 同时承担发布职责而自动扩张为数据库、安全、全局商业审计或正式版本流程；实际包含迁移、构建链、合规后台或发布时，必须按更高等级如实归类。
- 迭代阶段运行受影响范围的检查；面向公网的最终状态完成现行构建、完整测试和适用专项门禁一次。每日发布可以复用完全相同最终输入的可核验成功结果；聚合新改动、版本相关输入或产物变化后，只重跑受影响且已失效的门禁，正式 tag、Release 和远端一致性核验仍须执行。
- 现有构建或部署命令内部已经包含的检查，不在外层对同一输入机械重复；不在聚合命令中的变更集、身份、权利链、安全或发布专项门禁仍必须执行。参数化校验、自动凭据或已验证产物部署入口未实际实现前，不得假称可以使用或凭主观判断跳过现有脚本。

## 每日发布门禁

发布流程开始前先执行工作区租约门禁：列出同一 `cwd` 的 Codex 任务，排除当前 OP 任务和 Archived；其他任务当前轮次仍 active 时，使用事件式任务等待，总上限 30 分钟。等待期间保持只读，不通知、不唤起、不发送消息，也不按分钟高频轮询。任务需要用户处理、状态不可读、到期未完成或未明确释放时停止发布；全部释放后重新检查任务状态、`git status` 和完整 diff，再从反馈门禁开始。

1. 第一项必须检查后台新建/未处理反馈。只读取必要字段，不输出隐私。
2. 不使用带过期清理副作用的 `cloud-client.loadAdminFeedback()` 做门禁；使用最小只读查询或只读 RPC。
3. 认证、权限、网络、复现或验证受阻时停止发布，不提交半成品。
4. 检查 `git status`、完整 diff、最近 tag、`origin/main` 和当日是否已经发布版本。
5. 香港自然日每天最多一个正式版本；当日全部功能、修复和文档合并到同一版本。
6. 版本发布运行 `npm run build:web`、`npm test` 和改动范围要求的内容检查。
7. 同步更新 `package.json` 和 `package-lock.json`；只有长期项目事实变化时才更新 `README.md`，不再逐版追加历史 `CHANGELOG.md`。显式暂存文件，不使用 `git add -A`。
8. 根据上次正式发布以来的实际改动生成完整 GitHub Release，创建发布提交和 annotated tag，正常推送，绝不 force push。
9. 对比本地发布提交、`origin/main`、本地 peeled tag 和远端 peeled tag，确认本次应发布内容完整，并明确列出保留的其他改动。

README 只在项目定位、稳定核心能力、使用方法、架构、部署、安全或兼容性等长期事实发生漂移时使用 docs 提交修正，不改版本、不移动 tag。README 不写逐版本发布要点，GitHub Release 是版本更新与维护记录的唯一权威来源。
