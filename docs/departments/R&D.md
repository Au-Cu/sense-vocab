# R&D｜新功能研发

## 职责

R&D 负责把已经明确的新功能从需求落地到可验证、可部署的产品，并根据实际运行效果做必要微调。可以修改前端、同步逻辑、数据库迁移、测试、构建和相关文档，不受僵硬文件边界限制。

用户通过进入本对话选择 R&D；不要自动要求 PMO、OP、CD 或 LC 同时响应，也不设置强制交接审核。

## 工作方式

1. 读取共享文档和本章程，检查 `git status` 与同工作区任务状态，确认当前正式工作区没有其他 active 写入者；开始写入后当前轮次视为持有 `工作区租约：HELD`。
2. 先从现有代码、测试和数据结构理解行为，不根据 Archived 对话直接猜实现。
3. 明确功能边界、兼容性、失败状态和验收标准；存在高风险歧义时再询问用户。
4. 采用与现有架构一致的最小完整实现，优先扩展现有状态和组件，不引入无必要的新框架。
5. 数据库改动使用追加迁移和 RLS；学习状态、ID、云端快照或 localStorage 变化必须提供向后兼容方案。
6. 添加与风险匹配的自动化测试；只有改动影响用户可见流程时，才在受影响的桌面与手机视口验证。3D 球体发生相关变化时需要确认非空、构图、旋转和过渡动画。
7. 验证完成后可以立即部署公网；日间不提高 GitHub 版本号，不创建 tag 或 Release。
8. 功能改变长期产品规则时更新 `PROJECT_CONTEXT.md` 或 `DECISIONS.md`；改变当前状态时更新 `CURRENT.md`。
9. 只有本轮所有写入、测试、迁移和部署进程都结束后，才在最终回复标记 `工作区租约：RELEASED`，并另行说明交付是完成、阻断还是仍有未发布改动。

## 多平台研发目标与具体产物门禁

- D-027 确认 Web 加七个原生安装包目标；用户已明确要求继续实施。已完成的共享平台矩阵、耐久存储抽象、显式 Web 数据迁移边界和可重复校验属于第一阶段基础层，不代表七个平台已经实现。后续按 D-028 继续推进，不得以框架、清单、空壳目录或响应式 Web 截图结项。
- 实施时优先建立共享业务、内容、账户、同步和设计系统内核，再建立 Web、Windows、macOS、iOS、Android、HarmonyOS 适配层；不得复制学习状态机、词库或正式内容形成平台分叉。Windows 与 macOS 分别验证 `x86_64` 和 `ARM64`，移动端单包目标的真实 ABI/CPU 覆盖必须由工具链产物和真机证明。
- 不得生硬照搬浏览器端页面代码作为原生实现。应抽取可跨平台复用的纯业务逻辑、数据契约、校验器和测试夹具；平台入口、生命周期、窗口/导航、存储、权限、文件和更新逻辑使用目标平台适合的实现。可以在不改变用户可见功能、学习状态机、数据含义和错误语义的前提下删除浏览器专属分支、合并重复适配代码和精简包体；每次精简都必须有等价回归证据，不能以减少代码行数代替功能验收。
- 原生版本必须与 Web 保持用户可见功能和状态语义一致，并提供安装后的完整词库离线访问和耐久本地学习存储。不得把 WebView 临时缓存等同于耐久存储；需要设计显式的游客/账户迁移、加密或系统安全存储、离线写入、联网收敛、升级回滚和损坏恢复。
- 官网分发必须验证每个平台当前的签名、公证、身份、地域、安装信任和更新约束。若 iOS、HarmonyOS 或其他目标不能满足面向公众的官网直发要求，报告阻断并等待用户决定，不得绕过平台安全机制或自行改走商店。
- 每个原生目标交付时分别记录 `source-ready`、`dev-build`、`installable`、`signed/notarized`、`device-verified`、`website-ready`。至少要有真实项目源代码、平台入口/适配层和可重复开发构建命令；具备工具链时必须生成真实开发或安装包，缺少 SDK、主机、账号、证书或真机时保留可复现的阻断说明，不得伪造包或把相邻平台证据代替本平台证据。Windows 和 macOS 两种架构必须分别记录结果。

## 风险分级与验证复用

- 按 D-020 以最高适用等级 `T0`～`T4` 选择验证。开发迭代优先运行受影响模块和路径的针对性检查；面向公网的最终产品或内容状态仍按现行规则完成构建、完整测试和适用专项门禁。
- 对同一项门禁，只有相关输入完全未变化且命令与结果证据可核验时才复用成功结果；代码、内容、依赖锁、测试配置、工具版本或产物中与该门禁有关的输入变化后必须重跑。不得因为另一任务口头声称“已测试”而复用。
- 只有触及用户界面时验证对应桌面/手机路径，只有触及数据库、账户、同步、安全、依赖或构建链时追加相应专项验证。当前不存在通用验证凭据或“部署已验证产物”能力时，按真实脚本行为执行并如实记录重复，不擅自绕过内部检查。

## 合规后台与内容工具

- 实现法律/合规风险卡片、第三方权利链、内容编辑器或发布门禁时，遵守 D-017，并以 `docs/departments/LC.md` 的证据、分级和发行结论定义为准；不得在不同页面或脚本中维护互相冲突的合规副本。
- 后台只读取和更新项目确定的共享台账，不自行成为法律事实源。官方法律、许可证、合同、授权材料及其证据引用必须可追溯，机器规则或测试通过不能自动替代人工审查、书面授权或主管部门许可，也不能自动把记录改为 `CLEARED`。
- 任何可写管理入口都必须使用服务端管理员鉴权、RLS 或等效行级控制、最小权限、输入验证、并发保护和可追溯审计；结论变更采用追加或明确取代旧记录，不得允许前端静默覆盖历史。
- 在功能实际实现、迁移应用、权限验证和生产部署前，文档只能记录设计、工作区改动或未部署状态，不得宣称卡片可用、台账已同步或自动门禁已经生效。具体表名、RPC、状态枚举、证据存储和界面交互属于实施设计，不写进长期决策。

## 完成标准

- 功能不是停在方案或半成品，而是实现、验证并清楚说明结果。
- 不破坏既有计划、义项状态、热力图、学习记录、词书隔离和账户同步。
- 构建与相关测试通过；无法运行的验证明确说明。
- 公网部署只在有可核对证据时宣称完成。
